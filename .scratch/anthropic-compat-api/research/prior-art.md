# Prior art: HTTP surfaces over Claude Code and the Claude Agent SDK

Commissioned by: `.scratch/anthropic-compat-api/issues/05-prior-art.md`
Date: 2026-10-04
Method: GitHub repo and code search (`gh search repos`, `gh search code`, WebSearch), then reading each project's source files for request translation, process spawning, streaming and tool handling, plus its issue tracker. Every claim below cites a repository file path (default branch as of today) or an issue URL. No project was run; runtime behaviour is inferred from code, READMEs and the projects' own issues. Line numbers come from `nl -ba` over raw files fetched today and will drift.

Excluded on purpose:

- **Reverse-direction proxies** that let Claude Code talk to other model providers (1rgs/claude-code-proxy, fuergaosi233/claude-code-proxy, musistudio/claude-code-router and the many `anthropic-proxy` variants). They translate the Anthropic wire format but do not drive upstream.
- **Token-reuse proxies** that read Claude Code's OAuth token and call `api.anthropic.com` directly instead of running the CLI: router-for-me/CLIProxyAPI ("Claude Code support via OAuth login", [README L122](https://github.com/router-for-me/CLIProxyAPI/blob/main/README.md)) and horselock/claude-code-proxy ("borrow Claude Code subscription authentication to make normal API calls … probably not super cool in terms of ToS", [README](https://github.com/horselock/claude-code-proxy/blob/main/README.md)). Not the project's approach, and they sit on the wrong side of the billing gate described in "Operational pitfalls" below.
- coder/agentapi (★1500): drives the interactive TUI through a terminal emulator and exposes its own `/message` API, not a vendor surface; the README now says it is deprecated ([README](https://github.com/coder/agentapi/blob/main/README.md)).

## Per-project notes

### openchamber/opencode-claude (held-open run, OpenAI surface, Agent SDK)

The most complete tool bridge found. The file header states the design: "Tool calls from OpenCode are exposed as an in-process MCP server. When Claude invokes one, the stream parks (Cursor bridge-pool pattern) and returns tool_calls; the follow-up request with tool results resumes the turn" ([src/proxy.ts L1-L10](https://github.com/openchamber/opencode-claude/blob/main/src/proxy.ts)).

- **Half 1 (call out).** `buildOpenCodeMcpServer` wraps each client tool with `sdk.tool(name, description, shape, async (args) => { … pendingTools.set(id, pending); onPark(); const result = await resultPromise; return { content: … } })` (src/proxy.ts L1763-L1793). The consumer loop races the SDK iterator against a park notification and quiet/settle timers, and once the assistant message is closed and the expected parallel group has registered, yields `{ type: "__park__", tools }` and returns, which the HTTP layer renders as `finish_reason: tool_calls` (L1409-L1427). Ids are minted by the proxy: `` `call_${randomUUID()…}` `` (L1768).
- **Half 2 (result in).** On the next request, `collectToolResults` maps `role: "tool"` messages by `tool_call_id` (L473-L482); the bridge is found by conversation key or, as a fallback, by any pending `tool_call_id` (`findBridgeByPendingTool`, L705-L715; [src/bridge-pool.ts L63-L70](https://github.com/openchamber/opencode-claude/blob/main/src/bridge-pool.ts)); each pending call's `resolve(result)` is invoked and `existing.continueStream()` resumes consuming the same SDK iterator (L735-L776). Partial results re-emit the still-pending calls instead of starting a parallel run (L777-L792). Mid-turn user messages ride along on the last tool result ("steering", L718-L759).
- **Abandonment.** `armParkReap` closes a parked turn after `OPENCODE_CLAUDE_PARKED_TURN_TTL_MS` (1 h per CHANGELOG L156-L157); a stall watchdog fails a silent CLI truthfully (L1449-L1468); the SSE `cancel()` callback stops the bridge when the client disconnects mid-turn (L2407-L2414). Issue [#28](https://github.com/openchamber/opencode-claude/issues/28) records the gap that remained: while parked there is no open HTTP request, so `cancel()` never fires and the CLI child survived until superseded; the fix gives each query its own `AbortController`. `stopBridge` interrupts before rejecting pending calls, because "rejecting first would hand the CLI an error result it answers with another model call" (bridge-pool.ts L91-L96).
- **Schema fidelity.** Zod shapes are built with `z.fromJSONSchema(...).loose()` when available, else a hand-rolled mapper (L1688-L1762), and the server's `tools/list` handler is overridden to return the client's JSON Schema verbatim because "the SDK re-derives tools/list from zod, which drops parameter descriptions and narrows types" (L1803-L1812). Issue [#12](https://github.com/openchamber/opencode-claude/issues/12): a zod 4.5 shape fed to the SDK's bundled zod 4.4.3 converter made `tools/list` fail and the model ran with no tools.
- **Options.** `tools: []`, `allowedTools` = `mcp__<server>__*`, `permissionMode: "bypassPermissions"` only when bridging, `systemPrompt: { type: "preset", preset: "claude_code", append: … }`, `resume` per chat, `strictMcpConfig` via `isolateMcp` (L1273-L1341; src/query.ts L352-L397).
- **State.** Each OpenCode chat is one Claude session resumed every message; reverts fork the session at the right leaf (`sdk.forkSession`, src/query.ts L70-L76); only when no session exists is the history sent as a text transcript (L1176-L1184). README: "Each OpenCode chat maps to one Claude Code session and resumes it on every message. That keeps Anthropic's prompt cache warm."
- **Terms.** README has a "Terms of use: read this first" section citing Anthropic's Agent SDK article and listing the rules it keeps (CLI does all the talking, no token handling, no disguise, loopback only, plans only). See "Operational pitfalls" for issue #33.

### mazamaka/claudegate (held-open run, OpenAI surface, Agent SDK Python)

Docstring of [src/claudegate/bridge/session.py L1-L17](https://github.com/mazamaka/claudegate/blob/main/src/claudegate/bridge/session.py): a request ends when "the run finishes (`ResultMessage`), or the model asks for tools this client owns — at which point the conversation is left *standing*, blocked inside the tool handlers, and the HTTP response closes with `finish_reason: "tool_calls"`. Nothing is torn down in the second case."

- Long-lived `ClaudeSDKClient` per conversation, `connect()` once, per-turn `query()` with a raw user dict, pump task drains `receive_messages()` forever (L214-L287, L369-L372). Options: `include_partial_messages=True`, `permission_mode` default `bypassPermissions`, bare mode sets `system_prompt` to the client's string and `tools` to the client MCP tool names only (strips built-ins), `mcp_servers={"client": …}`, `allowed_tools`, `strict_mcp_config=True` (L122-L168).
- Half 1: on each `AssistantMessage`, every `ToolUseBlock` the toolbelt owns gets an `asyncio` future keyed by `call_<toolu_…>` (the model's own id, kept whole, [openai_api/outbound.py L31-L40](https://github.com/mazamaka/claudegate/blob/main/src/claudegate/openai_api/outbound.py)), then `ToolCallsRequested` and `TurnFinished(stop_reason="tool_use")` end the HTTP turn (session.py L449-L462). The MCP handler "Park[s] until the client sends this call's result back. The CLI is happy to wait: it is blocked on an MCP response" (L498-L526); it first waits up to `_REGISTRATION_GRACE_S = 30` because "the CLI dispatches tools/call on its own task, so it can beat the assistant message", then `claim()`s by name+args, name, or position ([toolbelt.py L157-L165](https://github.com/mazamaka/claudegate/blob/main/src/claudegate/bridge/toolbelt.py)), and awaits the future with `tool_wait_ttl_s` (600 s default).
- Half 2: `deliver_tool_results` sets each future's result; calls the client did not answer are force-released with a placeholder text "A client that answers only some of the calls would otherwise leave the conversation wedged until the TTL expires" (L289-L309). If the session is gone, `rebuild_on_expiry` replays history as text (manager.py L219-L226) else HTTP 409.
- Schema passthrough: the raw JSON Schema dict goes to `tool(mcp_name, description, schema)` (toolbelt.py L116-L127); names sanitised to `[a-zA-Z0-9_-]`, 60 chars.
- Session matching without `resume`: identity hash of model + system prompt + tools fingerprint + tenant, plus a rolling hash over user/tool messages and a "proof of receipt" that the client echoed the last assistant text ([bridge/continuity.py L13-L118](https://github.com/mazamaka/claudegate/blob/main/src/claudegate/bridge/continuity.py)). Limits: `max_sessions=64`, idle TTL 1800 s, `first_event_timeout_s=90` ("silent CLI = auth problem"), `request_timeout_s=900` ([config.py L110-L129](https://github.com/mazamaka/claudegate/blob/main/src/claudegate/config.py)).
- Gaps admitted or found: `tool_choice` only `"none"` honoured (`named_tool_choice()` has no caller); no periodic keepalive; no `/v1/messages`.

### cramt/claude-sub-proxy (held-open run, minimal)

- `captureToolCall` returns a Promise it never resolves itself and stores the call under `` `${sessionId}__${seq}` `` (server/lib/session.ts L113-L130); `scheduleFlush` batches handlers that fired in the same tick with `setImmediate` and resolves the HTTP boundary as `tool_calls` (L132-L146). `provideResults` resolves the stored promises and the same `for await` loop continues (L183-L194). The next request finds the session by parsing the session id out of `tool_call_id` and checking `knowsCall` ([server/lib/proxy.ts L87-L99](https://github.com/cramt/claude-sub-proxy/blob/main/server/lib/proxy.ts)); otherwise a fresh run with a text transcript.
- `canUseTool` auto-allows everything ("the *client* is the real gatekeeper", L75-L76) and built-ins are never disabled, so Read/Bash/WebSearch can run upstream unseen by the client. `includePartialMessages: false`; streaming is one chunk. No timeouts anywhere; an unanswered call hangs the HTTP request and leaks the run. JSON Schema → Zod via a hand-written mapper ([server/lib/json-schema-to-zod.ts](https://github.com/cramt/claude-sub-proxy/blob/main/server/lib/json-schema-to-zod.ts)) that drops `additionalProperties`, `const`, `allOf`, `$ref`, formats and bounds.
- README calls ToS "gray area … billing … in flux". The MooseGooseConsulting fork is byte-identical.

### AntonioAEMartins/claude-code-proxy (ended run, Anthropic surface, CLI subprocess)

The closest analogue to this project: TypeScript, a real `/v1/messages`, and a CLI subprocess rather than the SDK.

- Spawn ([src/cli/args-builder.ts L33-L95](https://github.com/AntonioAEMartins/claude-code-proxy/blob/main/src/cli/args-builder.ts)): `claude --print --output-format stream-json --verbose --include-partial-messages --dangerously-skip-permissions --no-session-persistence --model <opus|sonnet|haiku> [--effort] [--system-prompt <text>] --strict-mcp-config --mcp-config '<inline json>' --tools '' [--json-schema]`; the prompt is written to stdin and stdin closed (src/cli/subprocess.ts L36-L37); one spawn per request; `REQUEST_TIMEOUT_MS` 300 000 → SIGTERM then SIGKILL after 5 s; client disconnect kills the process.
- Streaming is a near-verbatim passthrough: `event: ${event.type}` / `data: ${JSON.stringify(event)}` of the upstream `stream_event.event` (src/translation/cli-to-anthropic-stream.ts L5-L7, L64), so `index`, `message.id`, usage and `stop_reason` are upstream's own, `tool_use` arrives as genuine `content_block_start` + `input_json_delta`, and `stop_reason: "tool_use"` is the real value from `message_delta`. The only mutation is stripping the `mcp__client_tools__` prefix (L28-L33). No `ping` keepalive on the Anthropic route.
- Tool bridge: `buildMcpConfig` turns `request.tools` into `{mcpServers:{client_tools:{command:'node',args:[mcp-bridge.js],env:{TOOL_DEFINITIONS}}}}` (src/translation/anthropic-to-cli.ts L104-L111); the stdio bridge registers raw JSON Schema through the low-level `Server` (src/tools/mcp-bridge.ts L19-L21, L55-L61) and returns a placeholder `{status:'pending', message:'Tool execution delegated to client…'}` (L63-L76). The proxy sets `sawToolUseStop` on `message_delta.stop_reason === 'tool_use'` and returns after the following `message_stop`: "The CLI would continue into a second turn with the MCP bridge's placeholder result — that garbage must never reach the client" (cli-to-anthropic-stream.ts L35-L38, L66-L72), then `finally { kill() }`. Issue [#1](https://github.com/AntonioAEMartins/claude-code-proxy/issues/1) documents the pre-fix behaviour: the CLI fed the placeholder back, the model answered it, and the client got that second turn with `end_turn`.
- Next turn: no pending map, no id matching. `tool_use` → `<tool_call id name>{json}</tool_call>`, `tool_result` → `<tool_result tool_use_id is_error>…</tool_result>` inside `<assistant_response>` wrappers (anthropic-to-cli.ts L22-L44, L74-L86); tools are re-registered on the fresh spawn. `tool_choice` is typed but never applied.
- Issue [#5](https://github.com/AntonioAEMartins/claude-code-proxy/issues/5): `McpServer.tool()` expects a Zod raw shape; given JSON Schema it registered `{type:"object"}` with no properties and "the model sees no parameters". Issue [#7](https://github.com/AntonioAEMartins/claude-code-proxy/issues/7): mapping two client tools to one built-in name (`Bash`) corrupted the reverse map and the agent looped forever.
- Web search: not recognised; `AnthropicToolDefinition` requires `input_schema`, so a schema-less `{type:"web_search_20250305"}` entry has no handling. Images unsupported, sampling params ignored (README L272-L278). CLAUDE.md L285 notes rate-limit headers are impossible once SSE has started.

### MehdiMohseni82/claude-code-proxy (ended run, Anthropic surface, Agent SDK)

- Three code paths on `/v1/messages`: plain, tool path (any `tools`, `tool_use` or `tool_result` present), and built-in path behind an `x-enable-builtin-tools` header ([src/routes/anthropic.ts L370-L482](https://github.com/MehdiMohseni82/claude-code-proxy/blob/master/src/routes/anthropic.ts)). Plain path streams SDK `stream_event`s with `message_start.message.id` rewritten; the tool path buffers the run and synthesises `message_start` → blocks → `message_delta{stop_reason}` → `message_stop`, with `tool_use` emitted as one `input_json_delta` carrying the whole input (L791-L885). `stop_reason` is `sawToolUse ? "tool_use" : "end_turn"`, not upstream's (L627).
- Tool bridge: in-process `createSdkMcpServer` named `proxy`, each tool `mcp__proxy__<sanitized>`, `allowedTools` lists exactly those; handler returns `"__PROXY_INTERCEPTED__"` with `isError: true`, relying on `maxTurns: 1` so "the SDK won't feed this back to Claude for another turn" ([src/services/toolBridge.ts L93-L153](https://github.com/MehdiMohseni82/claude-code-proxy/blob/master/src/services/toolBridge.ts)); the route collects `assistant` messages until the SDK's synthetic `user` message and treats `error_max_turns` as expected (anthropic.ts L578-L612). JSON Schema → Zod is "deliberately narrow + permissive" (unions become `z.any()`).
- Next turn: text replay `[called tool "X" with input: …]` / `[tool result (id=…)]: …` (anthropic.ts L146-L196); no `resume`.
- Web search is recognised: `isServerTool` matches `^[a-z_]+_\d{8}$`, maps `web_search` → `WebSearch`, `web_fetch` → `WebFetch`, `code_execution`/`bash` → `Bash`, `text_editor` → `Edit`, skips `input_schema` validation for them and runs with `maxTurns: 10` (toolBridge.ts L6-L20; anthropic.ts L220-L229, L535-L561). ## Design lessons for the tool bridge

### 1. Real `tool_result` round trips exist, but only as held-open runs inside the wrapper's own process, and never yet on an Anthropic surface

Three projects complete the round trip (openchamber/opencode-claude, mazamaka/claudegate, cramt/claude-sub-proxy). All three do the same thing: the client tool is registered as an in-process SDK MCP tool (`createSdkMcpServer` / `create_sdk_mcp_server`) whose handler awaits a promise or future; the HTTP turn ends with the tool call while the upstream run stays blocked on the MCP response; the next HTTP request resolves the promise and the same run continues (openchamber src/proxy.ts L1763-L1793 and L735-L776; claudegate session.py L498-L526 and L289-L309; cramt session.ts L113-L146 and L183-L194). claudegate's handler comment is the whole mechanism in one line: "The CLI is happy to wait: it is blocked on an MCP response, which is exactly the semantics we want." Nothing in their code, changelogs or issues mentions the CLI itself timing out a parked MCP call; the only timeouts are the wrappers' own (10 min claudegate, 1 h openchamber).

Everything else is an **ended run**: the handler returns a placeholder, the wrapper harvests the `tool_use` and kills or exhausts the run, and the next turn replays history as prose (`<tool_call>`/`<tool_result>` text in AntonioAEMartins, `[called tool …]` in MehdiMohseni82 and jackhax, a ```` ```tool_calls ```` fence in ttlequals0, text markers in GodYeh). That design has a documented cost on every CLI-driven attempt: the CLI feeds the placeholder back to the model and starts a second model call that must be suppressed (AntonioAEMartins #1; jackhax relies on `maxTurns: 3`; MehdiMohseni82 relies on `maxTurns: 1` and `error_max_turns`), the model never sees a native `tool_result`, and the history grows as text. LiteLLM looked at this and declared `custom_tools=False`.

Nobody has done the held-open run on an Anthropic `/v1/messages` surface, and nobody has done it while driving the raw CLI subprocess: the single CLI attempt (AntonioAEMartins) uses a stdio MCP child of the CLI, whose handler cannot reach the wrapper's pending request, so it had to end the run. For this project the lesson is that the handler must live where the pending HTTP request lives. With the raw CLI that means either the SDK control protocol over `--input-format stream-json` (ticket 04) or an MCP server the wrapper itself hosts and references from `--mcp-config` (an HTTP-transport MCP server would do; none of the surveyed projects tried it). Ticket 06 should test exactly this; the SDK projects prove the upstream side holds.

The held-open run comes with three obligations the SDK projects had to learn by issue: an idle TTL per parked run and a watchdog for a silent CLI (openchamber L1377-L1397, L1449-L1468; claudegate `tool_wait_ttl_s`, `first_event_timeout_s`); teardown when the client disconnects or never answers, including while no HTTP request is open (openchamber #28: the parked CLI child outlived the abort because the SSE `cancel()` never fires while parked; cramt has no timeouts at all and leaks); and ordering of teardown (interrupt first, reject pending calls second, or the CLI answers the rejection with another model call: bridge-pool.ts L91-L96).

### 2. Correlate by the model's own `tool_use` id and pass the client's JSON Schema through untouched

On the OpenAI surface the projects mint their own ids (openchamber `call_<uuid>`, cramt `<session>__<n>`, claudegate `call_<toolu_…>`) and need a fallback path to find the parked run when the client drops the session header (openchamber `findBridgeByPendingTool`). On the Anthropic surface the ids are upstream's `toolu_…` values already: AntonioAEMartins passes them through verbatim in the SSE and the client echoes them in `tool_result.tool_use_id`. So the Anthropic surface can key the pending-run map directly on upstream ids, which also matches the glossary's "tool bridge" definition. claudegate shows the one race to design for: the MCP `tools/call` can arrive before the `assistant` message that names the `tool_use` id, so the handler needs a short registration grace or must claim by name+args (session.py L504-L511, toolbelt.py L157-L165).

Schema handling broke in four separate projects: AntonioAEMartins #5 (`McpServer.tool()` turned JSON Schema into `{type:"object"}` with no properties), jackhax (`z.unknown()` for every property), MehdiMohseni82 ("deliberately narrow + permissive" conversion), cramt (drops `additionalProperties`, `const`, `allOf`, `$ref`, formats, bounds), and openchamber #12 (a zod version skew between plugin and SDK made `tools/list` fail silently). The two that got it right serve the client's JSON Schema verbatim: AntonioAEMartins switched to the low-level MCP `Server` with raw `tools/list`/`tools/call` handlers, openchamber overrides `tools/list` to return the original schema because the SDK "drops parameter descriptions and narrows types". A CLI-driven wrapper hosting its own MCP server can do this natively; it should never round-trip through Zod. Two more invariants from the issues: strip the `mcp__<server>__` prefix before the client sees the name (AntonioAEMartins #1, bug 2) and never map two client tools onto one upstream name (#7).

### 3. Disable built-ins when client tools are present, and decide who ends the message

Every project that bridged tools also switched built-ins off for that run (`--tools ''` in AntonioAEMartins and GodYeh, `tools: []` in openchamber and elizaOS, `tools=` client names in claudegate, `disallowed_tools=BUILTIN_TOOLS` in salaesp), because otherwise "the model [uses] Read/Write/Bash instead of the client's tools" (GodYeh #2). cramt did not and its built-ins run invisibly. The installed CLI 2.1.284 supports `--tools ""` ("Use \"\" to disable all tools") and `--strict-mcp-config`, so the policy from ticket 01 (pure model endpoint, no host tools) and the tool bridge want the same flags. Web search complicates this: MehdiMohseni82 is the only project that maps the Anthropic `web_search_YYYYMMDD` server tool to the built-in `WebSearch`, and its capture loop then appears to return the `WebSearch` `tool_use` instead of the answer, because the same "stop at the first tool call" logic serves both client tools and built-ins. A run with client tools **and** web search needs the tool bridge to distinguish built-in `tool_use` (let the run continue) from client `tool_use` (park), which is exactly what the MCP-name prefix gives for free. wende shows the failure mode when that distinction is missing: forwarding built-in `Read`/`Bash` `tool_use` to OpenClaw as `tool_calls` "causes an agentic loop", so the fork disabled tool forwarding entirely; codingworkflow still leaks built-in calls to clients that never defined them.

Streaming fidelity depends on the same decision. When the wrapper cuts the run at upstream's `stop_reason: tool_use` (AntonioAEMartins), the Anthropic SSE sequence is upstream's own and correct, including `input_json_delta` and genuine `stop_reason`; when it buffers and synthesises (MehdiMohseni82), `stop_reason` and `index` are invented. A held-open run never receives a `message_stop` for the parked message from the SDK/CLI (openchamber yields its own `__park__` event; claudegate emits `TurnFinished(stop_reason="tool_use")`), so the Anthropic surface must synthesise `message_delta{stop_reason:"tool_use"}` + `message_stop` on park and open a fresh `message_start` on resume. Both can be done from the `stream_event` passthrough the CLI already provides with `--include-partial-messages`.

## Operational pitfalls recorded across the trackers

- **Billing gate on "third-party" traffic.** Anthropic's article [Use the Claude Agent SDK with your Claude plan](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) (fetched today) says the June 15, 2026 change was paused and "Claude Agent SDK, `claude -p`, and third-party app usage still draw from your subscription's usage limits". Trackers tell a different story since late September 2026: openchamber [#33](https://github.com/openchamber/opencode-claude/issues/33) (2026-09-29, open) `API Error: 400 Third-party apps now draw from extra usage, not plan limits`, bisected by users to a single OpenCode-specific line in the appended system prompt ("Workspace root folder:"); gotgenes/pi-packages [#883](https://github.com/gotgenes/pi-packages/issues/883) bisected the same 400 to two phrases in an appended prompt under `systemPrompt: {type:"preset", preset:"claude_code", append}` and concluded "Anthropic's server scores the appended system text"; NousResearch/hermes-agent [#48176](https://github.com/NousResearch/hermes-agent/issues/48176) reports the same error for direct OAuth calls lacking the CLI's billing system block; anthropics/claude-code [#45048](https://github.com/anthropics/claude-code/issues/45048) shows the error text for a Claude Code user in April 2026 (closed as duplicate of #45013). openchamber's 1.3.x changelog now says the error is "shown once instead of a retry loop". None of this is confirmed by Anthropic in writing. Consequences for the spec: drive the real CLI (which carries its own billing header), prefer `--append-system-prompt` over `--system-prompt` and keep appended content small, do not retry this 400, and expect that a client's `system` text can trip the classifier through no fault of the wrapper. RichardAtCT #53 is the earlier (June) scare about the same policy.
- **Argument length, shell escaping and secrets in argv.** RichardAtCT #3 (`[Errno 7] Argument list too long` at 22 messages), sethschnrt #12 (E2BIG, fixed by stdin), GodYeh (prompt still in argv, stdin PR unmerged), codingworkflow passes prompt and system prompt in argv, AntonioAEMartins passes `--system-prompt` in argv. LiteLLM, sethschnrt/wende, thhuang and AntonioAEMartins write the prompt to stdin instead. wende found that going through the Windows `claude.cmd` shim lets `cmd.exe` interpret `<`, `>`, `(`, `)`, `&` inside an appended system prompt and silently corrupt the flags after it (manager.ts L97-L105), so spawn the real executable with `shell: false`. The current claude-wrapper `echo | claude --print` through `exec` shares both exposures.
- **System prompt replaced vs appended.** RichardAtCT #54 (dict shape silently dropped), MehdiMohseni82's `PROXY_SYSTEM_PREAMBLE` ("You are NOT Claude Code…"), salaesp's `LLM_GUARDRAIL` ("You have NO tools, NO file system…") and cramt's `settingSources: []` all exist because the Claude Code preset makes the model behave like a coding agent and "reference tools that don't exist in this context" (salaesp README). Inlining the client's system prompt into the user prompt is worse: thhuang PR #8 reports the model treating the inlined `<system>` block as "injected/spoofed content". openchamber keeps the preset and appends. Given the billing gate, appending is the safer default; replacing needs `--system-prompt` and a test against the 400.
- **Timeouts.** Defaults seen: 300 s (AntonioAEMartins, codingworkflow per line), 600 s (RichardAtCT), 900 s (claudegate request), 180 s (salaesp), 120 s (elizaOS), none (cramt). All far above claude-wrapper's 30 s. The stall watchdog (silence, not wall clock) in openchamber is the only one that distinguishes a slow model from a dead CLI.
- **Usage-limit and error mapping.** codingworkflow #48: `{"type":"result","is_error":true}` must be read from stdout, not stderr. MehdiMohseni82's `errorClassifier` infers 429/404 from CLI text because "Claude Code process exited with code 1" hides the cause. LiteLLM's `<synthetic>` model marker and `result.errors` are the structured route.
- **Concurrency.** RichardAtCT mutates `os.environ` per request; codingworkflow caps at 10 concurrent runs and returns 409 for a busy session; openchamber serialises spawns per conversation with a lock and stops a superseded turn before starting the next ("never runs two processes on one session", CHANGELOG 1.3.0).
- **Model names.** AntonioAEMartins resolves by family prefix and 400s unknown families (#14); sethschnrt #14 "Only very old models are reported"; claudegate aliases `gpt-4o`→sonnet; RichardAtCT fetches the live model list when an API key is present. The installed CLI accepts aliases `fable`, `opus`, `sonnet` or full names (`claude --help`, `--model`).
- **Streaming hygiene.** Heartbeats: codingworkflow `: heartbeat` every 30 s, openchamber `setInterval` heartbeat "for any hop that still kills silent SSE connections", thhuang axum keep-alive plus a `ping` event on `/v1/messages`, AntonioAEMartins none on the Anthropic route. Error frames without `[DONE]` (RichardAtCT) break OpenAI clients; an error delivered as an SSE chunk is one "the OpenAI SDK silently drops" (sethschnrt #2), so clients saw empty replies; claudegate guarantees error frame + `[DONE]`. thhuang #7: emitting both the `assistant` message content and the `content_block_delta`s doubled every reply; pick one source.
- **Auth state leaking from the host.** sethschnrt #2: a stale `CLAUDE_CODE_OAUTH_TOKEN` inherited from Claude Desktop's environment overrode the CLI login. wende and GodYeh strip `CLAUDECODE` from the child env; LiteLLM gives the CLI a private `CLAUDE_CONFIG_DIR` and `--setting-sources user`; elizaOS strips every `ANTHROPIC_*`/`*_API_KEY` variable except `CLAUDE_CODE_OAUTH_TOKEN`. The spawn environment is part of the contract.
