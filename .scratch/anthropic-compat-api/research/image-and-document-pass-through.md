# Image and document block pass-through upstream (2.1.289)

Research for ticket `issues/18-image-and-document-pass-through-upstream.md`. Date: 2026-10-04.
Upstream probed: `claude` 2.1.289 (`claude --version`, `cli-probes/o-pass-through-run1.harness.txt` line 1) at `~/.local/share/mise/installs/claude/latest/claude`, Claude subscription login, model `claude-fable-5-1`, `permissionMode: "default"`, `tools: []` (every `system/init` frame in both runs).

## Question

Which user content block sources does Claude Code forward to the API when they arrive in a `--input-format stream-json` user message? Known before this ticket: a base64 `image` block reaches the model ([CLI contract](cli-headless-io-contract.md) §3, probe `e-stream-json-input.jsonl`, 2.1.284). Block shapes are from the [wire contract](messages-api-wire-contract.md) §1.2.

## Method

- **Harness**: `cli-probes/o-pass-through.harness.py` (copied from `e-stream-json-input.harness.py`, then extended). It writes the test PDF, launches upstream once per run with stdin held open, sends one `{"type":"user","message":{"role":"user","content":[...]}}` line per block source, waits for that message's `result` frame before sending the next (120 s cap per message, then SIGINT, SIGTERM, SIGKILL; never needed), closes stdin at the end, and prints a per-message summary. `--set run1` and `--set run2` select the two message lists; the run-1 list is unchanged from the run.
- **Exact argv** (harness log line 2 of both runs): `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --replay-user-messages --tools "" --setting-sources= --strict-mcp-config --permission-mode default --permission-prompts none --max-budget-usd 1 --no-session-persistence`. `--permission-mode default` is accepted by the 2.1.289 parser even though `--help` lists only `acceptEdits, auto, bypassPermissions, manual, dontAsk, plan` (CLI contract §9 notes CR documents `manual` as an alias for `default`).
- **Hygiene**: cwd was an empty scratch directory under the session scratchpad (`probe-18/cwd`, `contents: []`, harness log line 3), not the repo; no `--dangerously-skip-permissions`. Each run is a fresh session (`--no-session-persistence`, distinct `session_id`).
- **Runs**: two. Run 1 (`o-pass-through-run1.*`, 63 frames, 17.3 s, exit 1) sent six messages cheapest-first: text document, content document, base64 PDF, url image, url document, then a text document carrying `title`, `context` and `citations`. Run 2 (`o-pass-through-run2.*`, 48 frames, 14.6 s, exit 1) re-tested the optional fields as the sole document of a fresh session and retried URL sources on other hosts; its last message (a 14-page PDF) was conditional and was sent only because every earlier URL block had failed. No message timed out; no 400 ended a run (see observations).
- **Test material** (all verified before the run): `o-pass-through.tangerine.pdf`, a 608-byte one-page PDF written by hand in the harness (`qpdf --check` clean, `pdftotext` returns exactly `The codeword is tangerine-7`); text document `The codeword is marigold-3`; content document `The codeword is cobalt-9`; citations document `The codeword is saffron-5` with `title: "Saffron memo"`, `context: "An internal memo supplied for the probe."`, `citations: {enabled: true}`. URLs, each HTTP 200 from this machine via curl: Wikimedia Commons PNG `.../4/47/PNG_transparency_demonstration_1.png` (800x600, 224 KB); W3C `.../resources/pdf/dummy.pdf` (1 page, 13 KB, served as `application/pdf; qs=0.001`); run 2: Wikimedia Commons JPEG `.../a/a7/Camponotus_flavomarginatus_ant.jpg` (759 KB); GitHub `raw.githubusercontent.com/github/explore/main/topics/python/python.png` (9 KB); `pdfobject.com/pdf/sample.pdf` (1 page, 19 KB); `assets.anthropic.com/.../Claude-3-Model-Card-October-Addendum.pdf` (14 pages, 2.6 MB), which is the URL [DOC-PDF] itself uses as its URL-source example (pdf-support.md line 124).
- **Prompts**: every message asked the model to quote the codeword of the document attached to *this* message (or describe the image) in one sentence and to say explicitly if it received no attachment. Codewords differ per block so a reply cannot be satisfied from an earlier block in the same session.
- **Primary docs** fetched 2026-10-04 as raw markdown (`.md` suffix): [DOC-CITE] https://platform.claude.com/docs/en/build-with-claude/citations, [DOC-PDF] https://platform.claude.com/docs/en/build-with-claude/pdf-support, [DOC-VISION] https://platform.claude.com/docs/en/build-with-claude/vision, [SIN] https://code.claude.com/docs/en/agent-sdk/streaming-vs-single-mode. Line numbers refer to the raw markdown.

Frame line numbers below are 1-based lines of the named `.jsonl`.

## Results

**No substitution anywhere.** All eleven `user` echo frames across both runs were identical to the content sent (`ECHO identical_to_sent=True` on every `<- type=user` line of both harness logs). The only `system` frames were `init` and `status: "requesting"`; no `system/api_retry` appeared in either run. The text-note substitution that [SIN] line 161 documents ("If an image block's `source` is missing or isn't an object ... Claude Code sends Claude a text note in place of the image, such as `[Image could not be processed: image block has no source object]`") concerns a malformed block and was not exercised; every block here had a well-formed `source`.

**The URL failures are the API's, not the CLI's, and not host-specific.** Six URL blocks over five hosts, three image and three PDF, including the exact PDF URL in Anthropic's own documentation, all returned the same `400 Unable to download the file` 0.6-2.9 s after the message was sent, each with a distinct `request_id` on the synthetic assistant frame (e.g. `req_011CfhQy8L3ByFqodjjJwibD`, run1 line 52) and `api_error_status: 400` on the result. The CLI therefore sent the block to the API as-is and the API's own fetcher refused or failed to download. What cannot be told from the client side is *why*: the URL feature is documented for the public API ([DOC-VISION] line 294 "URL-based image example", [DOC-PDF] line 105 "Option 1: URL-based PDF document"), so the likeliest reading is that URL sources are not fetched for requests on the path Claude Code uses (subscription OAuth with Claude Code's beta headers); an Anthropic-side outage on 2026-10-04 cannot be excluded. The 400s cost nothing (`total_cost_usd` unchanged across them), so the run-2 message set is a cheap re-check if URL support ever matters.

## Support list under the decision rule

Conversation state decision 9: a source upstream forwards is supported on the surface; a source upstream drops, substitutes, or that the API rejects is a 400 `invalid_request_error` naming the block type.

Supported (forwarded, model saw the content):

- `image` / `source.type: "base64"` (probe e).
- `document` / `source.type: "base64"`, `media_type: "application/pdf"` (row 3).
- `document` / `source.type: "text"`, `media_type: "text/plain"` (row 1).
- `document` / `source.type: "content"` (row 2).
- `document` fields `title`, `context`, `citations.enabled` (row 6), with the API-side constraint of row 6b: citations must be enabled on all document blocks in the request or on none, and "the request" means the whole upstream history, not just the current message ([DOC-CITE] line 370: document indices span "all messages").

400 `invalid_request_error` naming the block type:

- `image` / `source.type: "url"` (row 4).
- `document` / `source.type: "url"` (row 5).

Rationale for the url rows: the CLI forwards them, but the API behind upstream rejected every one; forwarding them from the surface would only relay the same 400 after a round trip and, per the observation below, leave the rejected message in the held-open run's history. Rejecting them up front is both cheaper and keeps the upstream session clean. If a later probe shows URL fetching working on this path, the rule's first clause would move both rows to "supported" with the upstream 400 passed through.

Not tested: `source.type: "file"` (Files API `file_id`, out of scope for the surface), `cache_control` on these blocks, `search_result` blocks, and malformed `source` objects (the [SIN] text-note path).

## Observations for other tickets

1. **A 400 does not end a streaming-input run.** After each 400 the process stayed alive and processed the next stdin message normally (run1: messages 3, 4, 5 each got their own `system/init`, echo, synthetic assistant and `result`; run2 likewise for messages 1-4). The shape of a rejected message's frames: an `assistant` frame with `message.model: "<synthetic>"`, `stop_reason: "stop_sequence"`, zero usage, `content: [{type:"text", text:"API Error: 400 ..."}]`, plus top-level `error: "unknown"`, `request_id`, `is_api_error_message: true` (run1 line 52); then a `result` with `subtype: "success"` **and** `is_error: true`, `api_error_status: 400`, `terminal_reason: "api_error"`, `stop_reason: "stop_sequence"`, `num_turns: 1`, zero usage and an unchanged `total_cost_usd` (run1 line 53). No `rate_limit_event` follows a 400. Both runs exited 1 when stdin was closed after an error result, where probe e (all successes) exited 0. Relevant to [Process lifecycle](../issues/19-process-lifecycle-and-concurrency.md) and to error mapping on the surface: `subtype` alone does not signal an error.
2. **A rejected user message stays in the upstream history.** The citations error of run 1 names `messages.9.content` for the sixth user message (run1 line 62). Three successful exchanges occupy indices 0-5, so index 9 means the two rejected URL messages (and more than their user halves alone would account for) were replayed in the next request. The exact composition (whether the synthetic error assistant frames are replayed, or an extra message precedes the first user turn) is unresolved and was not needed here. Consequence for [Conversation state](../issues/10-conversation-state-and-system-prompt.md) and the [tool bridge](../issues/07-tool-bridge-strategy.md): a block the API rejects pollutes a held-open run; validating block sources before forwarding avoids that.
3. **Citations come back only in `stream_event` frames.** With citations enabled the model answered in three text blocks; the CLI emitted one `assistant` frame per block, all with the same `message.id` (run2 lines 12, 19, 23). The citation itself appears only as a `content_block_delta` of type `citations_delta` (run2 line 15, requires `--include-partial-messages`); the CLI's assembled `assistant` frame for that block carries `citations: []` (line 19, same as the `content_block_start` at that index), and `result.result` is `"."`, the text of the last block only (line 28). A surface that supports `citations.enabled` must assemble the response from stream events and must not take `result.result` as the answer text.
4. **Cost and quota.** CLI list-price estimates: run 1 `total_cost_usd` 0.133 for three model calls (run1 line 48; the three 400s added nothing), run 2 0.106 for one call (run2 line 28). Fresh-session context with these flags: 3867 created + 531 read (run1 line 4) and 5188 created (run2 line 4, citations document). Five-hour utilisation from `rate_limit_event`: 0.28 at the first frame of run 1 (line 17, emitted after the first model call, so it already includes that call), 0.28 at the last frame of run 1 (line 47), 0.33 at the only frame of run 2 (line 27). Tickets 16 and 17 were released alongside this one and may have run concurrently, so the 0.05 rise between runs is an upper bound on this ticket's share. `rate_limit_event` was not emitted after every model call (run 1 had it after messages 0 and 2 but not 1).
